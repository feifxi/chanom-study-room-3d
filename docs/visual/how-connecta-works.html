1. The four programs

Connecta is four Node programs plus five services in Docker. The browser only ever talks to one address (localhost:3000); Next.js forwards three path prefixes to the other programs.

Postgres belongs to the API alone. The gateway and game server never read it; they get what they need from Redis or from signed passes.
Program Owns Never does
web apps/web every page, the 3D scene, the HUD decide anything: it asks the others
API apps/api/src/main.ts the database, sign-in, every rule and every write, background jobs hold live connections
gateway apps/api/src/gateway.ts each tab's one live socket; delivers what the API publishes; writes presence write anything else
game apps/game what's happening inside a room right now: positions, bubbles, games, timers, cats, who may talk read the database
shared packages/shared rules both sides run: maps, movement, collisions, protocol types, chess/slave rules, word filter run on its own
Why split it this way? Each kind of traffic has a different shape. REST is short requests that need the database. Live pushes are many idle sockets that rarely talk. A 3D room is a small group exchanging 15–20 messages a second, all in memory. Voice is heavy media. Putting each in its own process means each scales on its own (more gateway processes for more tabs, more game processes for more rooms) and a crash in one doesn't take down the others. The gateway is the same code as the API with a second entry point, so it shares the auth setup for free.
Why one origin? The session is an HttpOnly cookie. If the browser only calls localhost:3000/..., that cookie goes along to the API and the gateway automatically, so there is no CORS and no token in JavaScript. The same build works in every environment because every URL is relative.

2. Four lanes of traffic

Almost every flow in the app is one of these four, or a chain of them. Once you know the lanes, every feature reads the same way.

REST (HTTP)gateway (Socket.IO)game (Colyseus WebSocket)voice (LiveKit WebRTC)Redis (server ↔ server)
Lane Shape Used for Who decides
REST request → answer, through the typed client every write that should last: sign-up, rooms, chat messages, friends, Shop, payments, admin the API, against Postgres
gateway one socket per tab, server pushes "something changed, refresh": new message, friend request, inbox item, presence, typing dots the API publishes; the gateway only relays
game one WebSocket per room you're in; messages in, state patches out 20×/s everything inside a 3D room: moving, sitting, bubbles, focus timer, games, TV, cats the game server, from memory
voice WebRTC media streams through LiveKit (an SFU) microphones and screen shares game server says who may talk; each browser says who may hear it
Rule of thumb from the codebase: if it should survive everyone leaving, it's in Postgres and goes through REST. If it only matters while people are inside, it lives in the game server's memory. Servers talk to each other only through Redis, never by calling each other.

3. The trust chain: cookie → ticket → voice pass

Three different "who are you" credentials, each made by the one before it. This is the heart of how the API, the game server and LiveKit cooperate without sharing a database.

Why signed passes instead of letting the game server read Postgres? The decision log says it: otherwise the game server would need a second copy of every rule (memberships, bans, capacity, plans, timeouts) and the whole auth setup. With a ticket, the API decides once, and the game server only checks a signature, which is a few microseconds and needs no network call. The ticket is short-lived (60 s) because it's only for the moment of joining; once you're in, the WebSocket itself is the proof. The same trick is reused for room decks in Pick a Side (a "deck pass").
Why does the game server, not the API, sign LiveKit tokens? Who may talk changes inside the room (a mod mutes you, a time-out ends, you're a guest and the owner flips guest voice on). The game server is the one that knows that live, so it hands out the token and calls LiveKit's server API to change permissions on the fly.

4. Colyseus in 10 minutes

Colyseus is a Node framework for "authoritative" multiplayer servers. You write a Room class; Colyseus handles WebSockets, matchmaking, syncing state, and reconnection.

The five ideas

1. A Room is one live game instance in memory.
Connecta has exactly one room type, ConnectaRoom (apps/game/src/room.ts), and one instance per Connecta room. defineRoom(ConnectaRoom).filterBy(['place']) makes joinOrCreate with the same place (the room id) land in the same instance. The instance is created when the first person joins and disposed when the last leaves (autoDispose).
2. State is a schema, synced automatically.
state.ts declares RoomState with players, npcs, spots, watch, chess… using Colyseus schema(). The server just assigns fields (p.x = 3). Every 50 ms (patchRate) Colyseus sends each client a binary patch: only the fields that changed. Clients get a mirrored copy.
3. Messages go client → server.
The browser sends room.send('move', {x, z, yaw, seq}). The server lists handlers in messages = { move: validate(zodSchema, handler), … }. Every handler checks the sender may do it (in range, seated, the host, not timed out), then changes state. The client never changes state itself.
4. Private messages go server → one client.
Anything not everyone may see is not put in state (state goes to everyone). Instead client.send('slave:hand', …). Used for card hands, Draw & Guess turns, your voice token, "you're timed out", and bubbles inside a private zone.
5. A lifecycle you hook into.
onAuth (may this connection join?) → onJoin (add a Player) → onDrop (connection lost: allowReconnection(client, 20)) → onReconnect or onLeave → onDispose.
Matchmaking = HTTP, then WebSocket.
client.joinOrCreate(name, options) first does an HTTP request to the game server (/game/matchmake/...), which runs onAuth and reserves a seat, then opens the WebSocket for that seat. That's why /game/* is proxied with WebSocket upgrades.

The lifecycle, as Connecta uses it

  1. onAuth verifies the ticket (readTicket, jose.jwtVerify), checks it's for this room, and checks a seat with the shared hasSeat(capacity, role, inside): one seat is held for the owner and one for a mod. Throwing ServerError(403, 'full') refuses before any WebSocket opens.
  2. onJoin adds a Player to state.players (synced to all) and a Private record to priv (server-only: move budget, timer, time-out, pets). If the same account already has a connection here, the older one is closed with GAME_CLOSE.elsewhere ("newest tab wins"), and a running focus timer is carried over.
  3. It then tells presence (Redis) and publishes "walked in" so any other room this account is in, on any game server process, lets it go (one room at a time).
  4. onDrop: a flaky network keeps your place 20 s (RECONNECT_SECONDS); the SDK reconnects by itself.
  5. onLeave / remove: out of state, out of voice (removeParticipant), presence cleared, a running focus round counted.

Timers live on the server

onCreate starts the room's clocks: NPCs 10×/s, focus timers, TV and activities 4×/s, typing dots and time-out expiry every second, presence refresh every minute. Countdowns in the browser compare against the game server's clock (learned with a ping on join, lib/serverClock.ts), so a wrong computer clock can't change a timer.

In the browser

useGame.ts gets the ticket and joins. LiveRoom (features/room3d/liveRoom.ts) listens to Colyseus Callbacks (onAdd/onRemove on players and npcs) and onMessage handlers, and mirrors everything into plain objects the 3D scene reads every frame. Components call methods like room.say(text), room.sit(id) that just send messages.

Why Colyseus (instead of doing rooms over Socket.IO or in the API)? A 3D room needs an authoritative server: something that owns positions and game rules so a tampered client can't teleport or peek at hands. Colyseus gives that shape out of the box: per-room instances, delta-compressed binary state sync (cheap for 30 moving people), message validation, matchmaking by key, and reconnection. Writing that on Socket.IO means building state diffing and room lifecycle by hand. Keeping it out of the API keeps REST stateless; a room's memory lives in exactly one process.

5. LiveKit in 10 minutes

LiveKit is an open-source WebRTC media server (an SFU, Selective Forwarding Unit), self-hosted in Docker on :7880. Browsers send their audio to it once; it forwards each stream to whoever subscribes.

The vocabulary

LiveKit term In Connecta
Room named after the Connecta room id: one voice room per 3D room
Participant + identity one per person inside; identity = their Colyseus sessionId, so a voice maps straight to a character in state.players
Track + publish your mic (and screen share video/audio) is a track you publish. Cameras are never allowed.
Subscribe receiving someone's track. Connecta connects with autoSubscribe: false and chooses by hand every 250 ms.
Access token + grant a JWT signed with the LiveKit API secret: roomJoin, room, canPublish, canPublishSources. Signed by the game server (voice.ts).
Server API (RoomServiceClient) the game server changes things live: updateParticipant (allow/deny talking), mutePublishedTrack (away), removeParticipant (kicked, left)
Track subscription permissions the publisher tells LiveKit which identities may receive its tracks. This is how private zones are enforced.
Why LiveKit? Proximity voice for up to 30 people on phones rules out a P2P mesh (each phone would upload 29 copies). An SFU uploads once. LiveKit is open source and self-hostable (no per-minute bill), has solid browser and Node SDKs, server-side permission control, and per-subscriber selection, which is exactly what "hear only the 12 nearest" needs. Voice is never recorded and never goes through our servers' CPU.

6. How API, game server, LiveKit and gateway work together

The full picture of one person walking in and talking. Each server does one job; they meet through signed passes and Redis.

  1. The page asks the API for a ticket with the session cookie. The API checks membership, bans, time-outs, plan capacity, and signs the JWT. Answer: { place, ticket }.
  2. The browser calls joinOrCreate('connecta', { place, ticket }). Colyseus matchmaking (HTTP) runs onAuth: signature, room id, seat.
  3. The WebSocket opens; onJoin adds you to state. Colyseus sends the full state, then patches 20×/s.
  4. The game server publishes your presence to Redis; the API's gateway process picks it up and pushes "Fei is in Library" to friends' tabs.
  5. The game server also publishes "walked in": any other room you're in drops you (GAME_CLOSE.otherRoom).
  6. The browser's voice hook sends voice; the game server answers privately with { url, token }, a LiveKit token where canPublish depends on role, mute and time-out.
  7. The browser connects directly to LiveKit with WebRTC (the one connection not through :3000) and publishes its mic.
  8. Every 250 ms the browser reads positions from the Colyseus state and tells LiveKit which tracks it wants (nearest 12) and who may receive its own (same zone).
  9. When something changes (a mod mutes you), the game server calls LiveKit's server API; LiveKit stops your mic at once even if your browser is tampered with.
The key insight: LiveKit knows nothing about 3D. The Colyseus state is the single source of "where is everyone", and both sides of voice read it: the game server for may you talk, each browser for whom do I hear and how loud. Using the Colyseus sessionId as the LiveKit identity is what joins the two worlds.

7. Sign-in and guests

Passwordless. Better Auth runs inside the API under /api/auth/*: a 6-digit email code, Google, Discord, and anonymous guests.

Email code sign-in

  1. /login calls authClient.emailOtp.sendVerificationOtp({ email }) (lib/auth-client.ts). Better Auth stores a Verification row and the mail module sends the code (Mailpit locally).
  2. authClient.signIn.emailOtp({ email, otp }): Better Auth checks it, finds or creates the User, and creates a Session row. Before that, databaseHooks.session.create.before refuses suspended/banned accounts, so no way in works for them.
  3. The answer sets an HttpOnly cookie (connecta.session_token) holding only a random token. JavaScript can't read it.
  4. The page calls GET /api/me to see which onboarding step is missing (birthday → character/handle) and continues there. Those are Connecta's own fields (handle, birthday, look), marked input: false so only the accounts module can write them after checking rules.

Every later request

A global guard in Nest protects every route: it reads the cookie, looks the session up, and gives the handler the user via @Session(). Public routes opt out with @AllowAnonymous() or @OptionalAuth(). Server components in Next forward the request's cookies when they call the API (getMe, getRoom), so pages render signed-in on the server. The gateway does the same check as Socket.IO middleware before the socket opens (auth.api.getSession with the handshake headers).

Guests

A guest pass link (/g/<code>) signs the browser in with Better Auth's anonymous plugin: a real account with a throwaway address on a domain that can't receive mail. PUT /api/me/guest sets a name, look and age answer. Accepting the pass writes a GuestVisit, so the ticket says role: 'guest' and the game server keeps them listen-only unless the room allows guest voice. Signing up later upgrades the same account and keeps the look.

Suspension, everywhere at once

The admin site's suspend deletes the sessions, calls LiveService.signOut(userId) (every tab is told and its socket dropped) and sends a kick room event so the 3D room drops them too.

Why Better Auth and database sessions (not JWTs)? It covers email codes, Google/Discord with account linking, anonymous guests that upgrade, and Postgres sessions out of the box; Nest's own auth package was too young. Server-side sessions can be killed instantly (suspension = delete rows), which a self-contained JWT can't. Passwordless means no password storage, resets or leaks; the cost is depending on email delivery.

8. REST and the typed client

The part you already know, with two twists: the schema is written once, and the browser never writes a URL or response type by hand.

  1. Each route declares its body and answer as Zod schemas (x.schemas.ts). Validation runs through StandardSchemaValidationPipe (@Body({ schema })), and Swagger reads the same schemas.
  2. pnpm api:client boots the API without listening, writes apps/api/openapi.json, then generates apps/web/src/lib/api/schema.d.ts.
  3. The web app calls api.POST('/api/rooms/{id}/ticket', { params }) (openapi-fetch): path, body and answer are typed. A wrong one fails pnpm typecheck, and CI fails if the generated files are stale.
  4. TanStack Query caches each answer under a key (['rooms', id]). Mutations update the cache first (optimistic) and roll back with a toast if refused. Live events (next section) mostly just invalidateQueries.
Why? One schema gives validation, docs and browser types, so the three can't drift. Optimistic updates make the app feel instant without the browser deciding anything.

9. Live events: how a chat message reaches everyone

REST writes; the gateway delivers. The API never holds sockets: it drops an event in Redis and every gateway process delivers it to its own sockets.

  1. When a tab opens a room's chat it sends watch; the gateway checks membership and joins the socket to the Socket.IO room room:<id>. Every socket is also in user:<id>.
  2. Sending is plain REST: POST /api/rooms/:id/messages. The API checks membership and time-outs, masks words, saves the Message.
  3. Then LiveService.toRoom(roomId, 'message', payload) publishes through Socket.IO's Redis adapter.
  4. Every gateway process (there may be many) hears it from Redis and emits to its sockets in room:<id>.
  5. The browser's one socket (features/chat/live.ts) gets it; useRoomChat updates the TanStack cache and the message appears.

Typing dots are the exception: typing goes browser → gateway → others, never stored. The gateway accepts only a handful of browser messages: watch, unwatch, watch:inside, typing, typing:dm, presence.

Why not send chat over the socket? Writes through REST get the same validation, typing, rate limits, tests and OpenAPI docs as every other call. The gateway stays tiny (check session, relay). Why Socket.IO rather than raw WebSockets? Automatic reconnects, rooms, and the Redis adapter that lets any API process reach any tab on any gateway process.

10. Presence: online, away, focusing, in which room

Two sources report, one writer computes. Each open tab is a row in Redis; only "last seen" is saved to Postgres.

  1. Each tab's socket sends presence with only how long it's been idle, when it changes and every minute.
  2. The game server reports which room each connection is in (and the focus subject) on GAME_CHANNELS.presence, on join, leave, focus changes, and every minute.
  3. The gateway (game-presence.ts) is the only writer: it updates presence:tabs:<userId> in Redis. A tab silent for 2.5 minutes drops off.
  4. Your status is computed from all tabs (online if any is active, away after 10 minutes, focusing from the game tab), then pushed to each friend's tabs, each with their own view (a private room they're not in is never named).
Why "which room" only from the game server? The browser could lie about where it is. The game server knows for certain who's connected to which room. Why Redis? It changes every minute for every tab and is worthless after a few minutes; Postgres would be wasted writes.

11. Walking into a room: from the Next.js page into the 3D world

What happens between clicking Walk in and seeing your character.

  1. Server render. /r/<id>/walk is a server component: it loads the room with your cookies (a private room you're not in is a 404) and renders WalkIn.
  2. Client-only loading. RoomLoader loads the 3D screen in the browser only (Three.js can't render on the server).
  3. Joining. useGame(roomId) waits one tick (so React's dev double-mount doesn't open two connections and kick itself), gets the ticket, and joins. It returns connecting, in with the room, or out with why (full, kicked, banned, elsewhere, otherRoom…), mapped from the WebSocket close code (GAME_CLOSE). WalkIn shows a card with the one next step.
  4. The screen. RoomView builds a LiveRoom mirror, the React Three Fiber canvas (RoomCanvas), and the HUD (Room card, tools, chat, people, dock). The map's data (walls, seats, zones in packages/shared/src/maps/library.ts) is used by both server and browser; its look (room3d/Library.tsx) only by the browser.
  5. Every frame the 3D scene reads the mirror (plain objects, no React re-render per patch), eases other people toward their latest synced position, and draws name tags and bubbles as one DOM layer over the canvas.
  6. Leaving is only the Leave button; every link out goes through a confirm (LeaveRoomLink), because leaving costs your voice, seat and timer.
Why a mirror instead of reading Colyseus state in React? Patches arrive 20×/s; re-rendering React that often for 30 people would wreck phones. The scene reads plain objects inside useFrame; React only re-renders the HUD on meaningful changes.

12. Moving: client prediction and server reconciliation

Waiting for the server before moving would feel laggy, so you move at once and the server checks you after.

  1. Each frame, keys / joystick / click-to-walk move you locally, using the same speed and collision code the server uses (packages/shared/src/movement.ts, collision.ts). Click-to-walk paths come from A* over a grid built from the furniture (navigation.ts).
  2. 15 times a second, move { x, z, yaw, moving, seq } goes to the server with a sequence number.
  3. The server refills a move budget by elapsed time, spends it on the distance, clamps to walls and bounds (rules.ts), and stores p.moveSeq = seq.
  4. The patch comes back with your position and the last seq applied. reconcile.ts compares it with what you predicted for that same seq and corrects smoothly only if they disagree (a cheat or a desync).
Why a shared package? Prediction only works if both sides compute the same result. Putting movement, collisions and maps in packages/shared means one copy of the rules, imported by both the browser and the game server.

13. Bubbles, private zones and Away

  • Bubbles are messages, not state: say { text }. The server trims to 120 chars, masks words if the room filters, refuses if timed out (answers privately with quiet { until, by } so you're told why), rate-limits (400 ms; 3 s in Common rooms), then broadcasts said. Not saved anywhere: they're spoken, not chat.
  • Private zones are rugs in the map data. If the speaker stands in one (and isn't using Talk to everyone), the server sends said only to clients standing in the same zone, instead of broadcasting.
  • Away: the browser reports 10 idle minutes (away { on }). The server shows 💤 in state and calls LiveKit's mutePublishedTrack so a forgotten tab doesn't broadcast the room. Never while a focus round runs.
  • Typing dots are a state field that clears itself if the client goes quiet.

14. Voice by distance: who may talk vs who hears

Two separate questions, answered in two places.

May you talk? The game server decides.
refreshVoice() in room.ts computes hushed = Common room, or guest without guest voice, or muted for everyone, or timed out. When it changes, voice.allow() calls updateParticipant(..., { canPublish }). LiveKit unpublishes your mic itself. A tampered browser can't get around it.
Whom do you hear? Your browser decides.
useVoice.ts runs a loop every 250 ms: for each remote voice, read their position from Colyseus state, skip if out of range / other zone / muted-for-me / deafened; sort by distance; subscribe the 12 nearest; set volume (full ≤ 2.5 m, silent at 9 m) and pan left/right with a Web Audio StereoPannerNode.

Private zones: enforced by the speaker's client

In the same loop, your browser calls localParticipant.setTrackSubscriptionPermissions(false, [...]) listing only the identities allowed to receive your mic: people in your zone if you're in one, people outside zones if you're not (everyone on Talk to everyone). LiveKit refuses anyone else. So someone outside a zone with a modified client can't subscribe to voices inside.

A talking indicator comes from a tiny level meter (AnalyserNode) per voice, quicker than LiveKit's own speaker events.

Why this split? From the decision log: LiveKit's server API can't set who receives someone else's track, and a separate LiveKit room per zone would drop your voice every time you stepped on a rug. So the publisher (you) sets who may receive you. Distance volume is a comfort setting, not security, so it's fine for each listener to compute. Subscribing to only 12 keeps bandwidth and CPU sane on phones in a full room.

15. Mod tools and room events: API → game server

Two kinds of moderation actions, two paths. In-room voice controls are game messages; anything that lasts is REST, then a room event so people inside feel it at once.

Kick (lasting: REST + room event)

  1. The mod calls DELETE /api/rooms/:id/members/:userId. The API checks canActOn (shared: mods never act on the owner or another mod), deletes the membership, writes an audit row (roommod.kick).
  2. GameService.roomEvent({ type: 'kick', roomId, userId }) publishes to Redis GAME_CHANNELS.rooms.
  3. Every game server process hears it; dispatch finds the room in its liveRooms map (only one process has it) and calls apply(event).
  4. apply removes them from state and LiveKit and closes their socket with GAME_CLOSE.kicked; their useGame maps the code to kicked and shows the card.
  5. LiveService tells their other tabs to refresh their room list.

The same path carries ban, role (🛡️ tools appear live), timeout, map (everyone sees a loading screen and lands at the new door), look (a new outfit shows wherever you are: roomId: '*'), plus, guestVoice, filterWords, notice, deleted.

Mute for everyone / Talk to everyone (live only: a game message)

The mod's browser sends mute or stage over Colyseus. The server allows it only for owner and mods, updates its muted set, and calls refreshVoice → LiveKit. It lasts until lifted or the room empties, so it never touches the database.

Why Redis pub/sub rather than the API calling the game server over HTTP? The API doesn't know which game process holds which room, and there may be many. Publishing once lets the right one pick it up. It also means the API never waits on the game server; if a room is empty, the event just goes nowhere.

16. Screen share and Watch together

Screen share
The browser sends share { where: 'tv' | 'table' }. The server checks you're on the TV rug or seated at a desk, and that nobody else shares there, then sets p.share in state. The picture and sound are LiveKit tracks; your browser lets only that audience receive them (same subscription-permission trick as zones), and they subscribe. Sound goes only to the audience, not by distance. The 3D TV shows a card, never the live video (a video texture would cost every phone).
Watch together (YouTube)
The TV is game state (watch.ts): which video, when it started, paused, Up next. watch:add looks the link up with YouTube oEmbed on the server first, so a broken or private video never reaches anyone and titles can't be made up. Each browser plays the video itself in a YouTube player and seeks back in line when it drifts more than 2 s. No video bytes go through our servers.

17. Activities and games: one flow for every game

Every game plugs into one framework on the game server (activity.ts), so chess, Slave, Pick a Side and Draw & Guess share the same lobby, start, results.

  • Being in the area is being in. The server watches positions and seats: sitting at the card table or stepping on the rug puts you in the lobby; 30 s out of the area puts you out. No "join" button message needed.
  • A game is a class implementing RoundGame (start, out, standing, stop, tick). The framework calls it; the browser's ActivityHud draws the same lobby, top strip and results for all, and each game adds its own panel or 3D layer.
Game Technique worth knowing
Chess Every move checked on the server with shared rules (packages/shared/src/chess.ts, on chess.js). The browser runs the same code to highlight legal squares.
Slave (cards) Hidden information. State holds only the public table. Each hand goes to its owner alone with client.send('slave:hand'), so a player inspecting network traffic still can't see others' cards.
Pick a Side The server reads where each player stands on the rug when time ends to count answers. A quiz answer appears in state only at the reveal. Room decks come from the API as a signed deck pass (same idea as the join ticket).
Draw & Guess Everyone works at once on chains. Each player gets only their own turn privately (tel:turn). At time-up the server asks each page for its draft (tel:collect). Drawings go up in pieces to stay under Colyseus's message size limit.
Whiteboard Not in state: strokes are relayed as messages (board:start/add/undo/clear) as 0–1 coordinates, kept in memory so newcomers get board:all. A per-person budget stops floods.
Why everything on the game server? Fair play needs one referee: the server deals cards, checks moves and runs timers on its own clock. Putting each game behind one interface means one lobby UI and one flow for players (an AGENTS.md rule: "one flow for every activity").

18. Focus timer, quests and background jobs: game server → API

The game server has no database, so things that must be saved go to the API as BullMQ jobs on Redis.

  1. focus:start starts a timer in the server's private record; your status and subject sync to everyone via state. The server's clock ticks it, so the minutes are real.
  2. When a round of 1+ minute ends (or you stop or leave), links.focusRound(round) adds a job to the focus-rounds queue with jobId: round.id.
  3. The API's worker (focus.processor.ts) saves a FocusSession. The job id means a retry never counts twice. Guests get the timer but nothing is saved.
  4. Quest steps (focus minutes, petting a cat, finishing a game, bubbles, time with others) go the same way on quest-events; quests.processor.ts adds progress and pays coins once, in the same transaction, as a CoinEntry.

Other jobs: pictures (WebP + picture check). Timed sweeps use @Cron (finish account deletions after 7 days, delete old guests, Plus ending every 10 minutes).

Why a queue instead of pub/sub here? Pub/sub is fire-and-forget: if the API is restarting, the message is lost. A BullMQ job waits in Redis and retries with backoff, so a finished focus round survives an API restart. Room events (kick, map) use pub/sub because they only matter right now.

19. Pictures: presigned S3 uploads

  1. POST /api/pictures: the API checks size and rate, makes a Picture row, answers a presigned PUT link.
  2. The browser uploads the bytes straight to S3 (locally through /api/dev-storage, because the AWS Emulator refuses browsers).
  3. POST /api/pictures/:id/uploaded queues a pictures job: shrink to WebP (≤ 2048 px), run the picture check (OpenAI moderation, off without a key).
  4. Then the message shows. Viewing is GET /api/pictures/:id: a members-only redirect to a one-hour link.
Why? Bytes never pass through the API, so a big upload can't tie up API servers. Room thumbnails reuse the exact same path.

20. Common rooms: public rooms for strangers

  • No database rows. A Common room is a type (library, cafe, rooftop); each copy is just a game server room id like common-library-2.
  • POST /api/common/:type/ticket: the API picks a copy from presence: your friends' copy, else the busiest still taking strangers (25 of 30), else a new one. A fresh ticket holds its seat in Redis for 30 s so two people never get the same last seat.
  • The ticket says common: true; the game server turns on safe rules: text only (no LiveKit at all), 3-second bubble limit, word filter always on, no TV.
  • Team actions inside (time out follows them into any copy; remove for an hour) live in Redis.
Why copies? A private room is "full is full", but a public place should always have room. Copying keeps each instance at the 30-person 3D budget.

21. Plus and Stripe

  1. POST /api/billing/checkout: the API creates a Stripe Checkout session; the browser goes to Stripe's page (card details never touch Connecta).
  2. Stripe calls POST /api/billing/stripe-webhook. The signature is checked over the raw body. The API records a Payment and moves users.plus_until forward.
  3. The change fans out: a live event (your tabs refresh) and a plus room event (your name tag sparkles in 3D).

Plus is just one date. Everything asks hasPlus(user), or roomPlus(owner) with a 7-day grace; limits come from ROOM_PLANS. Without Stripe keys a local stand-in marks it paid through the API, so the rest is the real flow. When Plus ends, a sweep resets rooms to Free limits; nobody is sent out, the game server just stops letting extra people in (capacity comes in the next ticket).

Why trust the webhook, not the browser coming back? The browser's "success" redirect can be faked or never arrive. Stripe's signed server-to-server call is the proof of payment.

22. Moderation, reports and the admin site

  • Word filter: one function, maskWords in packages/shared/src/moderate.ts, used by the API (chat, decks) and the game server (bubbles, Draw & Guess). Names with a blocked word are refused.
  • Platform settings (word list, switches, Common seats) live in Postgres; the API writes the whole set to Redis and publishes it, so every API process and game server applies a change at once.
  • Reports (POST /api/reports) also count in a Redis sorted set per person and place over a time window. 3 in 10 minutes in a room → automatic 15-minute time-out (sent as a timeout room event); 5 in 30 minutes in Common rooms → out for an hour. Each step writes an audit row with no by.
  • Team is a flag set only by a script. /admin answers 404 to everyone else, and every /api/admin/* route checks again. Every team action is an AuditEntry.
